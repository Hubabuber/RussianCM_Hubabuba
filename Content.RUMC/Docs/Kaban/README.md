# Кабанкоины RuCMU

## Статус реализации

Это отключённая по умолчанию система наградной валюты игрового аккаунта. Кошелёк,
покупки, изменения баланса и привилегии хранятся в действующей игровой БД.
Она не продаёт валюту за деньги, не поддерживает переводы, торговлю, приоритет
подключения, позднего входа, отрядов, квалификации или боевые преимущества.

Реализованы прямое управление балансом менеджерами, магазин, обычные и гибкие приоритеты
для обычного распределения профессий, заявки на персональные TTS, очередь выдачи
личных Discord-ролей через существующего бота, интерфейсы и русский/английский FTL.

Форсирование режима, планеты, GOVFOR/OPFOR и полного набора использует постоянную
очередь будущих раундов. Модуль отдельно включается через `rucm.kaban.forcing`.
Сервер проверяет каталог, резервирует цену и подтверждает исполнение после старта;
отменённые или неприменимые заявки возвращаются без потери заработанного.

Приоритеты в Force on Force недоступны. Гибкие приоритеты поддерживаются
обычным алгоритмом: первый подходящий конкурентный розыгрыш привязывает жетон
к одной из выбранных профессий. Они не меняют остальные предпочтения персонажа.

## Архитектура

* `Content.RUMC/Shared/Kaban`: CVars, запросы и приватные состояния EUI.
* `Content.RUMC/Server/Kaban`: экономические правила, интеграция БД,
  подготовленные приоритеты, TTS и Discord.
* `Content.RUMC/Client/Kaban`: окно и кнопки в лобби и Escape.
* `Content.RUMC/Database/Kaban`: EF-модель.
* `Content.RUMC/Database/Migrations`: миграции обоих провайдеров;
  общие снимки EF обновляются генератором.
* `Content.RUMC/Tests/Kaban`: проверки реальных провайдеров.
* `Content.RUMC/Resources/Locale`: русский и английский FTL.
* `Content.RUMC/Docs/Kaban`: документация, проверки и пример конфигурации.

Все новые файлы системы находятся в `Content.RUMC`. Существующие проекты подключают
её подкаталоги; `Content.Server.Database` отдельно подключает `Content.RUMC/Database`.
Пространства имён `_RuCM` сохранены, как и сборки EUI/EF и идентификаторы миграций.
В общих каталогах остаются точки интеграции, общие снимки EF и правка существующей
проверки миграции профилей. Ресурсы используют существующее подключение
`Content.RUMC/Resources`, сохраняя прежние виртуальные пути `/Locale/...`.

Следующие миграции этой системы нужно создавать в том же каталоге:

```powershell
dotnet ef migrations add <Name> --project Content.Server.Database --context SqliteServerDbContext -o ../Content.RUMC/Database/Migrations/Sqlite --namespace Content.Server.Database._RuCM.Migrations.Sqlite
dotnet ef migrations add <Name> --project Content.Server.Database --context PostgresServerDbContext -o ../Content.RUMC/Database/Migrations/Postgres --namespace Content.Server.Database._RuCM.Migrations.Postgres
```

Сервер берёт автора из аутентифицированной EUI-сессии. Клиент передаёт только
запрос, UUID операции и явное подтверждение покупки с показанной ценой. Повтор
UUID с тем же содержимым возвращает прежний результат; смена автора/содержимого
отклоняется. Операции, кошелёк, покупка, привилегия и аудит коммитятся вместе.
Неуспешная транзакция откатывается целиком. При неопределённом сетевом результате
нужно повторять **тот же UUID**, а не создавать новую покупку.

Перед чтением изменяемых экономических данных транзакция обновляет единственную
строку `rucm_kaban_lock`. Это сериализует решения нескольких процессов через БД,
включая прямые изменения баланса и недельные ограничения жетонов. SQLite выполняет блокирующий ввод-вывод в пуле
`ServerDbManager`, как остальные операции проекта. Игровой цикл не ждёт БД.
Недоступная экономика не отменяет стандартный запуск раунда.

`rucm_kaban_wallet` хранит баланс и общее заработанное; `ledger` — неизменяемые
изменения; `operation` — результаты идемпотентных запросов; `award` и `approval` —
архив прежних представлений и согласований (больше не используются); `product` — цены и доступность; `purchase` — чеки;
`token` и `token_use` — жетоны, резервы и использование; `voice` — текущая заявка,
`voice_claim` — постоянная принадлежность имён моделей; `discord_role` — роль и
очередь доставки; `round_request` — очередь форсирования;
`audit` — критические действия. Префикс таблиц — `rucm_kaban_`.

Ledger, операции, покупки и аудит защищены триггерами от UPDATE/DELETE, в SQLite
также от замены существующего ключа через REPLACE. Любое изменение менеджером
создаёт новую транзакцию с автором и получателем. Начисления увеличивают lifetime
earned; списания и возвраты его не меняют. Отрицательный баланс запрещён.

Модель содержит ограничения неотрицательных балансов, положительных сумм/цен,
внешние ключи покупок/привилегий, уникальное имя персональной модели. Миграции
не изменяют таблицы профилей. Недельные ограничения жетонов — скользящие семь
суток UTC, а не календарная неделя. Месячных ограничений начислений нет.

## Настройка

Все параметры серверные. Ни один из них не принимается из клиентского запроса.

| CVar | По умолчанию | Назначение |
| --- | --- | --- |
| `rucm.kaban.enabled` | `false` | Экономические операции; при выключении окно показывает пояснение |
| `rucm.kaban.shop` | `false` | Покупки |
| `rucm.kaban.priorities` | `false` | Покупка/активация/применение приоритетов |
| `rucm.kaban.forcing` | `false` | Резерв; форсирование всё равно заблокировано |
| `rucm.kaban.tts` | `false` | Заявки и использование новых персональных голосов |
| `rucm.kaban.discord` | `false` | Покупки и доставка Discord-привилегий |
| `rucm.kaban.managers` | пусто | UUID уполномоченных через запятую |
| `rucm.kaban.senior_managers` | пусто | UUID высшего руководства; также имеют обычные полномочия |
| `rucm.kaban.server_id` | `RussianCM` | Уникальный стабильный ID **этого процесса/сервера** |
| `rucm.kaban.discord_guild` | пусто | ID Discord-сервера |
| `rucm.kaban.discord_boundary_role` | пусто | Роль, строго ниже которой выдаются личные роли |

На нескольких серверах с одной БД обязательно задайте разные `server_id`.
Одновременный запуск двух экземпляров с одним ID не поддерживается: восстановление
резервов считает этот ID единственным владельцем. Не меняйте ID при наличии резервов
без их сверки. Перечни руководителей меняет оператор сервера через конфигурацию;
обычный административный флаг сам по себе не даёт права начислять КБК.

Цены и отключение отдельных товаров доступны высшему руководству в панели.
Старое подтверждение с другой ценой не списывает деньги. Исходный ассортимент:

| ID | Товар | КБК |
| --- | --- | ---: |
| `priority3` | Приоритет ×3, 30 дней | 60 |
| `priority5` | Приоритет ×5, 30 дней | 150 |
| `pack3` | Три приоритета ×3, по 45 дней | 165 |
| `pack5` | Три приоритета ×5, по 45 дней | 420 |
| `flex3` | Гибкий ×3, 30 дней | 100 |
| `flex5` | Гибкий ×5, 30 дней | 190 |
| `mode` | Форсирование режима — заблокировано | 350 |
| `map` | Форсирование карты — заблокировано | 250 |
| `govfor` | Форсирование GOVFOR — заблокировано | 200 |
| `opfor` | Форсирование OPFOR — заблокировано | 200 |
| `full` | Все четыре параметра — заблокировано | 800 |
| `voice` | Персональный TTS | 600 |
| `discord` | Постоянная личная Discord-роль | 300 |
| `rename` | Переименование/цвет существующей роли | 50 |

## Управление балансом

Менеджер открывает `kabancoins` → «Управление» → «Изменить баланс».
Выбирает игрока из списка или вводит сикей игрового аккаунта, указывает `+500` для начисления
или `-100` для списания и нажимает «Применить изменение». Комментарий необязателен.
Операция применяется сразу: нет представлений, согласований, месячного фонда,
лимита получателя или отдельного исключительного решения. Менеджер может
менять собственный баланс. Обычный игрок не может изменять баланс.

Полномочия задаются серверными `rucm.kaban.managers` (UUID через запятую)
или `rucm.kaban.senior_managers`; старшие также имеют полномочия менеджера.
Стандартный флаг администратора автоматически этого права не даёт.
После изменения списка обновите окно. Для проверки собственного баланса
достаточно одного менеджера: начислите себе 600 КБК этой формой.

Сикей проверяется без учёта регистра. Если имя неоднозначно, операция отклоняется.
Нулевое изменение, неизвестный аккаунт и списание больше остатка отклоняются
целиком. Автор, получатель, сумма и комментарий сохраняются в неизменяемом
журнале. Повтор того же запроса не начисляет и не списывает повторно.
Прежние таблицы награждений сохранены для истории без удаления данных;
старые действия представления/согласования больше не принимаются.

## Инструкция игроку

Откройте «Кабанкоины» в лобби/Escape или командой `kabancoins`.
Кошелёк показывает баланс и общую сумму наград. В магазине выберите товар,
прочитайте ограничения и отдельно подтвердите стоимость. Временная ошибка допускает
повтор **того же запроса** кнопкой «Повторить». Полный журнал хранится в БД;
в окне показываются последние 100 операций/наград/записей аудита.

Приоритет сначала покупается, затем активируется в лобби до подготовки карты.
В разделе «Приоритеты»: 1) выберите жетон в списке, 2) отметьте роль (до трёх для
гибкого жетона), 3) проверьте выбранные роли внизу и нажмите «Активировать».
Список строится из видимых ролей персонализации текущего режима, без повторов ID.
Скрытые, нерегистрируемые в меню и роли других режимов нельзя передать вручную.
Фильтр каталога общий с редактором персонажа. Изменение режима обновляет список. Профессия должна оставаться
разрешённой персонажу: жетон не открывает вайтлист, GOVFOR, баны, таймеры или другие
ограничения. Не выбирайте Never в обычных предпочтениях: жетон их не меняет.
Отменить активацию можно до начала подготовки. Новый раунд требует новой активации.

Вес равен 1, 3 или 5; вероятность очередного выбора — вес / сумму весов оставшихся
кандидатов. Выбор нескольких слотов идёт без возвращения победителя в пул.
Конкуренция определяется по всем оставшимся слотам профессии на станциях.
Если все претенденты помещаются, жетон не расходуется. При проигрыше конкурентного
розыгрыша расходуется. Назначенный ранее игрок не вытесняется. Приоритет применяется
только в обычном round-start распределении, включая командные профессии.

Резерв создаётся в БД заранее и входит в ограничения: один активный, четыре за
семь суток, из них два командных, один командный ×5. Гибкий резерв, содержащий
командную профессию, временно занимает командную квоту; после использования
учитывается фактически разыгранная профессия. Срок жизни резервов не продлевает жетон.
При отсутствии конкуренции или неудачном запуске резерв возвращается. При аварийной
остановке с незафиксированным результатом следующая загрузка возвращает жетон;
это сознательный выбор в пользу сохранности покупки.

## Персональные TTS

Стандартные голоса и существовавшие до системы custom-модели остаются доступными.
Покупка создаёт заявку на новое имя и хранит свидетельство разрешения владельца
голоса/прав. Она не обучает модель. Руководитель проверяет разрешение и загружает
согласованный образец через существующий механизм TTS. Самостоятельная загрузка
игроками запрещена, включая старую донорскую кнопку. Выключение экономики не
восстанавливает свободную загрузку новых голосов; старые модели сохраняются.

Высшее руководство также может создать бесплатную заявку по особому решению:
в панели указываются другой получатель, новое имя модели, разрешение и обоснование,
с отдельным подтверждением. Сохраняется чек с нулевой стоимостью и аудит; КБК
не начисляются и не расходуются. Загрузка модели и техническая проверка остаются
обязательными, самовыдача запрещена.

После загрузки руководитель подтверждает заявку в панели. Сервер запрашивает
реальный каталог и выполняет ограниченный по времени пробный синтез. Только после
успеха выдаётся доступ. Один аккаунт имеет одну текущую персональную привилегию.
Отклонение ожидающей заявки возвращает цену по отдельной транзакции.
Имена отвергнутых/заменённых моделей остаются закреплёнными и не становятся общими.
Новые персональные модели фильтруются в каталоге и при синтезе локальной речи,
радио, объявлений и предпрослушивании. Чужая/недоступная модель заменяется стандартной.

При старте до загрузки реестра персональных моделей custom-голоса временно
недоступны; стандартные работают. При последующей неисправности сохраняется
последний загруженный реестр. При первом успешном чтении каталога общие старые
модели фиксируются в БД единожды; новые неизвестные имена закрыты на всех узлах.
Состояние персональных голосов обновляется при операциях окна и раз в минуту.
Выдача/отзыв на другом узле может отражаться с задержкой до минуты; неизвестная
новая модель до обновления не становится публичной.
Выключение экономики/персональных TTS закрывает новые персональные голоса,
сохраняя стандартные и не принадлежащие новой системе старые модели.

## Магазин и локальный просмотр интерфейса

Окно открывается командой `kabancoins` или кнопкой в персонализации,
над списком персонажей, рядом с личным делом.
Баланс с иконкой монеты виден во всех разделах. Магазин содержит поиск,
категории и карточки товаров с иконками, ценами и доступностью.
«Подробнее» открывает условия и оформление покупки; согласие и итоговая
кнопка остаются под прокручиваемым содержимым. Сервер повторно проверяет
показанную цену. При изменении цены согласие сбрасывается. Повтор после
неопределённого ответа отправляет исходную операцию с тем же UUID.

Локальный просмотр работает только после отключения от игрового сервера:

```text
kabanpreview catalog
kabanpreview checkout minimum
kabanpreview inventory
kabanpreview priorities
kabanpreview admin
kabanpreview off
```

Команда использует демонстрационные данные и не отправляет запросы серверу.
Снимки каталога, оформления, инвентаря, недоступности и ожидания в двух размерах:

```powershell
dotnet bin/Content.Client/Content.Client.dll --self-contained --cvar display.width=1280 --cvar display.height=900 '+kabanpreview capture'
```

Результат находится в `bin/Content.Client/user_data/KabanPreview/`;
после сохранения клиент завершает работу. Это проверка интерфейса, а не
покупок или внешних интеграций. Русские и английские строки находятся в
`Content.RUMC/Resources/Locale`; после обновления ресурсов перезапустите клиент.

## Discord и руководство администратора

### Ошибка десериализации при открытии меню

Если клиент падает ещё при запуске с `Sandbox violation` и
`System.Text.Json.Serialization.JsonIgnoreCondition`, нужна версия с серверной
настройкой JSON: сетевой `KabanRequest` больше не содержит JSON-атрибутов.
`Unknown opcode: Conv_ovf_u1` в этом стеке возникает при диагностике запрещённой
ссылки загрузчиком. Проверки загрузчика должны оставаться включёнными.

Клиент и сервер должны быть собраны из одной версии общего кода. После изменения
`KabanState` или `KabanRequest` пересоберите оба проекта и полностью перезапустите
оба процесса. Старый клиент может подключиться, но не прочитать новое состояние EUI.
Для одной локальной сборки одинаковой конфигурации можно сверить общую библиотеку:

```powershell
Get-FileHash bin/Content.Client/Content.Shared.dll
Get-FileHash bin/Content.Server/Content.Shared.dll
```

Локальный `kabanpreview` открывает состояние напрямую и не проверяет сетевую
передачу. Отдельные `KabanSerializationTests` проверяют round trip полных сообщений
через NetSerializer, включая вложенные записи и nullable-поля.

### Привязка игрового аккаунта

Привязка встроена в игровой сервер: тот же бот, токен, жизненный цикл и
настроенная игровая БД. Поддерживаются SQLite и PostgreSQL. Отдельные
`Content.DiscordBot`, `config.json`, строка подключения и `!create` не нужны.
Сам механизм привязки не зависит от включения экономики или магазина.

### Обязательная привязка для игры

`rmc.discord_account_linking_required` по умолчанию `false`. На боевом сервере,
после настройки и проверки канала привязки, включите его в локальном конфиге:

```toml
[rmc]
discord_account_linking_required = true
```

Либо выполните в серверной консоли `cvar rmc.discord_account_linking_required true`;
для сохранения после перезапуска используйте конфиг. Общие конфиги и пример
оставляют настройку выключенной. При включении непривязанный игрок остаётся
в лобби с окном привязки: готовность, вход в раунд, наблюдение и гост-роли
блокируются сервером, включая административную принудительную готовность.
После привязки доступ открывается без переподключения. При включении во время
раунда управление непривязанным персонажем временно снимается, тело сохраняется;
после привязки или отключения требования игрок возвращается к нему.

Учитывается сохранённая привязка игрового аккаунта, а не наличие роли, доната
или текущее соединение бота. Уже привязанные игроки могут играть при недоступном
Discord. Пока данные аккаунта не загружены, доступ закрыт. Для временного снятия
требования установите cvar в `false`; настройки магазина менять не требуется.

В конфигурации игрового сервера заполните существующую секцию `[rmc]`:

```toml
[rmc]
discord_token = "ТОКЕН_БОТА"
discord_account_linking_channel = "ID_ТЕКСТОВОГО_КАНАЛА"
```

Перезапустите сервер. Боту нужны права видеть канал, читать историю и отправлять
сообщения. Он ищет в истории свою прежнюю кнопку, обновляет её либо создаёт
одну новую. При ошибке или тайм-ауте чтения истории новая кнопка наугад не
создаётся. Используйте отдельный канал привязки; на общей БД и с одним ботом
автопубликацию в этом канале настраивайте только на одном игровом сервере.
После запуска в журнале будет `Account-link button ready: ...`.
Временная ошибка публикации повторяется раз в минуту. Бот запускается после
инициализации локализации и игровой БД; его перезапуск завершает прежний worker.
Ссылка `rmc.discord_account_linking_message_link` выставляется автоматически и
передаётся клиентам. Пустой channel отключает новую привязку.

Для самой привязки и выдачи ролей сервер запрашивает только `Guilds`, без
privileged intents. Если настроен мост административного/менторского чата,
дополнительно нужны `GuildMessages` и разрешённый в Discord `Message Content`.
Настройки токена и канала применяются при старте/перезапуске бота.

Кнопка «Привязать Discord-аккаунт» находится в «Настройки → Основное».
Команда `discordlink` в F3 открывает то же окно без административных прав,
после подключения к серверу. «Личное дело» и кабанкоины расположены в
персонализации, над списком персонажей; под «Наблюдать» этих трёх кнопок нет.
Если бот ещё подключается или канал не настроен, окно остаётся доступным:
показывает пояснение, а «Открыть канал» включается автоматически при получении
ссылки. При новом открытии запрашивается свежий код, при отключении окно закрывается.

Игрок открывает «Привязать Discord-аккаунт» в настройках, копирует код, переходит
по кнопке в Discord и вводит его в закрытой форме «Привязать игровой аккаунт».
Код сначала сохраняется в БД и только затем отправляется игроку. Он действует
менее 24 часов и удаляется в одной транзакции с успешной привязкой и записью
аудита. Повторное использование и одновременный ввод с разных Discord не
создают две связи. Пустые/неизвестные/устаревшие коды отклоняются.

Успех показывается только автору формы, статус подключённого игрока обновляется
без переподключения. Старые `RMCLinkedAccounts` и спонсорские привилегии сохраняются;
магазин сразу использует ту же запись. Чужая существующая связь не заменяется:
конфликт требует обращения к администрации. Новый встроенный обработчик не
синхронизирует донатные уровни из Discord — для них остаётся штатный `rmcboosty`.
Старый отдельный бот для привязки нужно остановить, чтобы два обработчика
не отвечали на одну форму. Токен храните только в локальном серверном конфиге.

### Выдача купленных ролей

Используется существующий `RMCDiscordManager` (Discord.Net), его штатный токен
`rmc.discord_token`, существующая проверенная привязка `RMCLinkedAccounts`.
Новые токены/секреты в запросах или в журнале экономики не передаются.
Дополнительный процесс или второй токен для выдачи роли не нужен.

Игрок указывает название и HEX-цвет. Сервер проверяет привязку, допустимые символы,
длину и запрещённые названия; руководство вручную одобряет заявку, чтобы исключить
имитацию руководства и обход проверки похожими символами. После одобрения доставка
выполняется отдельно от покупки, максимум одна заявка за минуту, с тайм-аутом 30 с.
Недоступность Discord не влияет на кошелёк или игровой цикл.

Нужны подключённый штатный бот, `Manage Roles`, указанный guild и защитная роль.
Личная роль должна быть строго ниже защитной; бот должен быть выше неё. Выдаваемая
роль имеет нулевые permissions, без hoist/mentionable. Существующие роли с таким
названием, управляемые роли, @everyone и роли выше границы не используются.

При доставке бот поднимает личную роль сразу под защитную. Список ролей заново
запрашивается после создания (создание сдвигает позиции), а после перестановки
граница и нулевые права проверяются повторно. Ошибка перестановки оставляет
доставку в очереди, а не помечает её завершённой.

Чтобы личный цвет был виден в нике, расположите роли так:

```text
Роль бота
КБК-граница
Личные роли
Обычные цветные роли: Контрибьютор, Боец и т. п.
@everyone
```

Цвет ника берётся из самой высокой цветной роли. Цветная служебная роль выше
границы продолжит определять цвет; бот не пересекает эту границу. Уже выданную
активную личную роль можно один раз вручную перетащить под границу — повторная
покупка не нужна. Автоматический подъём выполняется при новых доставках,
их повторах и одобренных переименованиях, без создания второй роли.

Сначала создаётся нулевая временная роль `kbk-<UUID без дефисов>`, её Discord ID
фиксируется в БД, затем применяются название/цвет и назначение. Повторная доставка
использует сохранённый ID. Сбой после создания до фиксации ищет временную роль по
тому же имени. Неоднозначность или удалённая извне роль требует ручной сверки;
система не создаёт вторую роль наугад. Резерв доставки защищён двухминутной арендой
между процессами. Изменение привязки возвращает заявку на рассмотрение.

Ожидающую заявку можно отклонить с возвратом. После начала внешней доставки
автоматический возврат запрещён: результат может быть неопределённым. При отказе
переименования существующая роль и её прежние параметры сохраняются. Нельзя вручную
удалять записи очереди или выдавать возврат, пока не установлен внешний результат.

Высшее руководство меняет цены и доступность товаров в панели. Обычные менеджеры
управляют балансом через форму «Изменить баланс». Не редактируйте ledger, purchase,
operation или audit через SQL; используйте новые операции.

## Форсирование будущих раундов

Покупатель выбирает параметры из серверного каталога. Режимы берутся только из
`ShowInVote`, планеты — из развёрнутого пула режима; взводы — из списков планеты
и только для сторон, поддерживаемых режимом. Учитываются минимальный/максимальный
онлайн режима/планеты, наличие файлов планеты/её уровней, кораблей и техдеревьев взводов.
Границы онлайна вспомогательной корабельной карты не ограничивают население всего
сервера: корабли загружаются напрямую тем же путём, что при обычном голосовании.
Произвольные значения CVar клиент не передаёт. Одинаковые ID удаляются.

В заявке на один параметр сохраняется только этот параметр. Например, оплаченный
GOVFOR ограничивает голосования режима/планеты совместимыми вариантами и выбор
GOVFOR указанным взводом. Другие параметры остаются на обычном голосовании.
Полный набор выбирается последовательно: режим → планета → GOVFOR → OPFOR;
один и тот же взвод на обеих сторонах запрещён. Корабли полного набора — первые
допустимые корабли соответствующих взводов, если планета размещает сторону на корабле.

Покупка, резерв цены, очередь и аудит коммитятся под общей экономической блокировкой.
UUID покупки защищает от повторного списания. У аккаунта может быть одна ожидающая
заявка. На каждый `server_id` действует отдельная FIFO по времени покупки; равное
время разрешается сортировкой ID. Два игрока могут купить одновременно, но за один
раунд применяется одна заявка; остальные ждут следующего. Покупка после начала
голосований относится к будущему лобби. В разделе «Форсирование» видны статус,
параметры и место в очереди. Отмена владельцем/менеджером разрешена до захвата заявки
и полностью возвращает цену; начатую заявку отменяет администрация изменением
настроек или перезапуском.

Голова очереди захватывается в пуле БД до голосований. Ожидание ограничено пятью
секундами: при задержке/сбое начинается штатное голосование, поздний результат
возвращается. Подготовка и применение происходят в игровом потоке без ожиданий БД.
Полный набор сначала разрешает все зависимости, затем применяет режим, планету,
оба взвода, корабли, техдеревья, камуфляж и зависимые угрозы; старая последовательность
отменена и её таймеры защищены поколением. Перед загрузкой карт каталог и выбор
проверяются повторно, старые голосования фиксируются/отменяются.

Административная блокировка режима имеет приоритет. Ручная смена режима, планеты,
взвода/корабля или перезапуск отменяет активный платный план с возвратом.
При отмене восстанавливается режим, выбранный до платной заявки. Результат
подтверждается после `InRound`; несовпадение режима при fallback возвращает
цену. Неисправность экономики не должна удерживать штатный запуск. Завершение и
возврат идемпотентны, ошибки БД повторяются с паузой 30 секунд.

После первой загрузки карт выбор зафиксирован. Отключение модуля в этот момент
останавливает будущие заявки, а уже загруженный план завершается обычным путём;
настройки загруженного раунда автоматически не переписываются. После успешного
старта ограничения исполненного заказа снимаются с голосований следующего раунда.

Ограничения считаются по успешным исполнениям: одно за скользящие 7 суток; для
полного набора дополнительно один полный набор за 30 суток. Возвраты не занимают
эти лимиты. Неисполненная голова после изменения условий возвращается, следующий
покупатель получает следующий раунд.

При старте процесса незавершённые `applying` этого `server_id` возвращаются; `queued`
сохраняются. Если процесс аварийно завершился сразу после старта раунда, до записи
подтверждения в БД, применяется возврат в пользу игрока. Такой раунд не считается
подтверждённой покупкой. Не запускайте два живых сервера с одним `server_id`.
FoF использует `ForceOnForceAssignment.Assign`: совместное назначение с ценами
предпочтений и балансом сторон, а не независимые розыгрыши профессий. Вмешательство
в стоимость не соответствует формуле вероятностей 1/3/5. Нужен согласованный
взвешенный розыгрыш среди одинаково допустимых оптимальных назначений, сохраняющий
баланс и допуски. До этого FoF не расходует и не применяет приоритеты.

## Безопасное развёртывание и восстановление

1. Не сливать/не включать автоматически. Сделать резервную копию игровой БД
   штатным средством провайдера. Проверить восстановление копии отдельно.
2. Остановить игровые процессы, мигрировать копию текущей БД обоими применимыми
   провайдерами; проверить профили, привязки, квалификации и отсутствие pending model
   changes. На production применяется только провайдер production.
3. Развернуть с выключенными модулями. Дождаться загрузки реестра и восстановления
   резервов. Настроить менеджеров и уникальный server_id.
4. На тестовом сервере включить экономику и магазин. Проверить начисление,
   списание, покупку, повтор UUID и перезапуск. Затем включать приоритеты.
5. Проверить в настоящем клиенте CO/XO/баны/вайтлист/GOVFOR/таймеры, отсутствие
   конкуренции, проигрыш, несколько слотов, отмену запуска. Сначала использовать
   тестовые аккаунты, а не реальные награды.
6. TTS включать после проверки прав на модель. Discord — после теста границы ролей
   на отдельном guild. Форсирование включать после проверки очереди и реального запуска на тестовом сервере.

При инциденте отключите затронутый модуль и сохраните БД/логи. Не удаляйте журнал и
не обнуляйте кошельки. Невыполненные DB-транзакции откатываются провайдером; завершённые
распознаются по UUID. Резервы жетонов возвращаются на следующем старте того же
server_id; ошибки завершения повторяются с паузой 30 секунд и квота остаётся занятой.
Не снимайте резерв одновременно с живым сервером, который ещё может его применить.
Discord сверяется по delivery UUID, lease и RoleId. Откат схемы удаляет экономику:
на действующей БД после появления покупок используйте выключение модулей и исправление
вперёд, а не down migration. Восстановление старой копии потеряет последующие покупки,
поэтому требует отдельного решения и сверки.

## Проверка

### Одновременные запросы и конкуренция

| Ситуация | Результат |
| --- | --- |
| Два игрока с ×3 претендуют на одно место на одном уровне предпочтения | Равные шансы; при участии в конкуренции расходуются оба жетона |
| ×3 против ×5 на одном уровне предпочтения | 3/8 и 5/8 при двух кандидатах; при большем числе кандидатов веса суммируются |
| Свободных мест хватает всем кандидатам | Жетоны не расходуются |
| Один аккаунт пытается активировать два жетона одновременно | Сохраняется только одна активация |
| Два менеджера одновременно меняют один баланс | Изменения сериализуются, записи не теряются; уход в минус запрещён |
| Сикей совпадает у нескольких записей, в том числе с разным регистром | Изменение отклоняется; UUID не позволяет перенаправить выдачу |
| Повтор завершённой выдачи после переименования аккаунта | Возвращается исходный результат без повторного начисления |
| Два игрока одновременно покупают форсирование | Обе заявки попадают в очередь без потерянных списаний; применяется только первая, вторая ждёт следующего раунда |

Высокий приоритет персонализации рассматривается раньше среднего и низкого.
Жетоны меняют вес только внутри текущего уровня после проверок допуска;
они не обходят вайтлисты, баны, квалификации и лимит свободных мест.
Гибкий жетон участвует только в первом подходящем конкурентном розыгрыше.
Одному игроку нельзя выдать две профессии: назначение удаляет его из остальных
списков кандидатов существующего `StationJobsSystem`.

### Автоматизированные проверки

`KabanEconomyTests` применяет полную цепочку EF-миграций в отдельные SQLite-файлы и
в новые PostgreSQL-БД с префиксом `kaban_test_`. Для PostgreSQL задаётся переменная
`KABAN_TEST_POSTGRES` на **отдельный тестовый кластер** с правом CREATE DATABASE;
без неё PostgreSQL-сценарии явно пропускаются. Игровая БД в тестах не используется.

Тесты покрывают конкурентные списания/повторы, сохранение earned, подтверждение цены,
атомарный отказ, прямые изменения баланса менеджером (включая свой), отказ обычному
игроку, отсутствие месячных ограничений, владение/сроки/возвраты жетонов,
командный ×5, очередь/возвраты/ограничения форсирования, TTS-заявки, Discord-привязку и неизменяемый журнал.
Математический тест перебирает все билеты распределения весов без статистической
погрешности. Это не заменяет живой многопользовательский запуск, визуальную проверку
окна, реальный NTTS и Discord: они должны быть отдельно указаны в PR как проверенные
или непроверенные. Итоговые результаты см. в `VALIDATION.md` рядом с этим файлом.
